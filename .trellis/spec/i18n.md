# Internationalization: self-built lightweight i18n

> 42 keys (en ↔ zh mirror), 1 module (`src/i18n/`), 0 runtime dependencies on `vscode.l10n`.

The extension ships with two parallel message tables in `src/i18n/messages/{en,zh}.ts`. Runtime resolution goes through `src/i18n/index.ts:t(key, ...args, lang?)`. UI text in extension code uses `t(...)` exclusively; package metadata (command titles, view titles, `viewsWelcome.contents`) uses VS Code's native `%key%` placeholder mechanism via `package.nls.json` and `package.nls.zh-cn.json`.

---

## Manual language override (08-23 ui-lang-toggle)

A status-bar toggle button (priority 99, next to the CTM item at 100) cycles through `auto → zh → en → auto` on each click. The chosen preference persists in the VS Code config setting `claudeTaskMonitor.language` (`auto`/`zh`/`en`, default `auto`, Global scope — personal preference, not workspace-scoped).

### Detection precedence

`detectLang()` (`src/i18n/index.ts`) returns:

1. The module-level `override` if set (set by `setLangOverride(lang)`).
2. Otherwise `vscode.env.language.toLowerCase().startsWith('zh')` → `zh`, else `en`.

The override is written by `extension.ts`'s `onDidChangeConfiguration` listener (single channel; see `src/extension.ts` ~L408) on every `claudeTaskMonitor.language` config change, and cleared (`undefined`) when the new pref is `auto`. `LangStore` itself does not touch the override — it stays decoupled from the i18n layer so the store can be unit-tested without VS Code's i18n state. All `t()` callers benefit transparently — no signature changes.

### Refresh on language change

`extension.ts:onDidChangeConfiguration` listens for `claudeTaskMonitor.language` and:

1. `langStore.syncFromConfig()` — re-read fresh value.
2. `setLangOverride(newPref === 'auto' ? undefined : newPref)` — propagate to `t()`. For `'auto'` this writes `undefined`, letting `t()` fall back to env (via `detectLang()`). For `zh`/`en` this writes the concrete lang so `t()` overrides env.
3. `statusBar.update(store)` / `applyBadge(treeView, store)` / `provider.refresh()` — re-render dynamic UI.
4. `langToggle.render()` — re-render the toggle button itself.

Subsequent notifications / toasts / quickPicks automatically use the new language (they're event-triggered, so they re-evaluate `t()` at fire time). No reload required.

### Static UI — out of scope (intentional)

Command Palette command titles, view titles, `viewsWelcome.contents` come from `package.nls.<locale>.json`, which VS Code resolves **once at activation** based on `vscode.env.language` (the user's display-language setting). Changing `claudeTaskMonitor.language` cannot affect these — they're a platform-level hard limit. The toggle button's tooltip explicitly states this so users don't expect otherwise.

## Module design — why self-built, not `vscode.l10n`

See the header comment in `src/i18n/index.ts:1-20`. Summary:

1. **No vsce/XLF toolchain** — `vsce package` requires `vsce localize` to extract strings into XLF files and merge them back. ~38 keys don't justify the build complexity.
2. **Compile-time key check** — `t('key')` is a string literal call site. Missing keys produce `console.warn` at runtime, but TypeScript can't catch typos at build. Acceptable because the symmetry test (below) catches drift.
3. **Caller controls lang** — for tests, `t(key, ...args, 'zh')` skips `detectLang()` and uses the passed lang. No `vi.mock` required when the caller passes lang explicitly.

Detection: `vscode.env.language.toLowerCase().startsWith('zh')` → zh, else en.

## Key naming convention

`<area>.<context>.<id>` — same area groups related keys for grep-ability.

Current areas:
- `status.*` — status bar text + tooltip (text, tooltip variants, suffix glyph)
- `notify.*` — desktop notification text + action button labels
- `onboarding.*` — onboarding card content + buttons + toasts
- `banner.*` — sidebar banner (jq-missing state)
- `hook.*` — install/reinstall toast
- `mute.*` — per-session mute/unmute toast
- `filter.*` — quickPick title/placeholder/labels
- `warn.*` — error toasts (no-selection)
- `jqInstall.*` — platform-specific install commands (Darwin/Linux/Win32)
- `badge.*` — sidebar activity-bar badge tooltip (added in 08-23)
- `status.label.*` — row description prefix per status (added in 08-23)
- `lang.toggle.*` — language toggle button state names + tooltip (added in 08-23)

When adding a key:
1. Add to BOTH `en.ts` AND `zh.ts` at the same relative position.
2. The symmetry test (`src/test/i18n.test.ts:103-109`) compares `Object.keys(en).sort()` to `Object.keys(zh).sort()` — failure here means the build is broken. Don't disable this test.
3. If the key is referenced in `package.json` (command titles, `viewsWelcome.contents`), use `%key%` placeholder and add to `package.nls.json` + `package.nls.zh-cn.json` instead of the runtime i18n tables.

## Placeholders

`{0}` `{1}` `{2}` — match the vscode.l10n convention. `t(key, arg0, arg1, ...)` replaces in order.

```ts
t('notify.single', displayNameOf(s.cwd), s.toolName)
// 'notify.single': '{0} 等待权限确认：{1}'
// → 'my-app 等待权限确认：Bash'
```

Missing placeholder (no arg for `{1}`): kept as literal `{1}` in output. Documented in `src/test/i18n.test.ts:86-88`.

## Deliberate non-fix: lang detection footgun

`t(key, ...args)` walks all args, treating any literal `'zh'` or `'en'` as a lang override and silently dropping it from the placeholder list. This means `t('foo.bar', 'en')` does NOT substitute `'en'` into `{0}` — it sets lang=en with zero placeholders.

Documented and tested in `src/test/i18n.test.ts:94-100`. Considered changing the API to `t(key, lang, ...args)` (explicit lang as first arg) but rejected:

- 42 keys enumerated — none pass `'en'`/`'zh'` as a placeholder value.
- Changing the API requires auditing 8+ call sites.
- Type system can't distinguish caller intent at runtime — the safer-looking `t(key, lang, ...args)` requires callers to remember the lang-first convention; current "lang anywhere" is more forgiving.

If a future key genuinely needs `'en'`/`'zh'` as a placeholder value, the fix is to refactor that specific key (rename the placeholder domain) rather than change the API.

## Test patterns

### Symmetry test (mandatory after every i18n key addition)

`src/test/i18n.test.ts:117-127`:

```ts
describe('i18n key 对称性', () => {
  it('en 和 zh 的 key 集合完全一致', async () => {
    const { en } = await import('../messages/en.js')
    const { zh } = await import('../messages/zh.js')
    expect(Object.keys(en).sort()).toEqual(Object.keys(zh).sort())
  })
})
```

The symmetry check runs in every `pnpm test` run. If you add a key to only one table, this test fails — catches the class of bug that produced Findings #2, #3, #5, #6 from commit `be68481`.

### Override test (added 08-23)

`src/test/i18n.test.ts` `describe('detectLang override ...')` block verifies:

1. Override takes precedence over `vscode.env.language`.
2. `setLangOverride(undefined)` reverts to env.
3. `t()` reflects override when no explicit lang arg is passed.
4. Explicit `t(key, 'en')` arg still wins over override (preserves caller-control semantic).

Both blocks use `beforeEach`/`afterEach` to call `setLangOverride(undefined)` — the module-level variable is shared across tests and must be reset.

### Module isolation for files that call `t()`

Any test file whose SUT calls `t()` must mock `vscode` so `detectLang()` doesn't reach the real vscode env. Established pattern (`src/test/notifyMessage.test.ts:7`, `src/test/statusBar.test.ts:7`, plus `badge.test.ts` and `rowPresentation.test.ts` added in 08-23):

```ts
vi.mock('vscode', () => ({ env: { language: 'zh-cn' } }))
```

Place this line **before** any `import` from the SUT module. vitest hoists `vi.mock` calls but the explicit pattern avoids surprises.

For tests that explicitly pass lang as the last argument (`t(key, arg0, 'zh')`), the mock is technically unnecessary, but add it anyway for consistency — makes the test's intent obvious to future readers.

See [[testing]] for the general mocking philosophy and vi.mock hoisting behavior.

## Package metadata localization

`package.json` uses `%key%` placeholders. VS Code resolves these against `package.nls.json` (English, fallback) or `package.nls.zh-cn.json` (Chinese, picked when `locale=zh*`).

Currently localized:
- 19 command titles (`%command.*.title%`)
- 1 view welcome content (`%welcome.content%`)
- `extension.displayName` and `extension.description`

Adding a new `%key%` placeholder:
1. Add the `%key%` literal in `package.json`.
2. Add `key: "..."` to BOTH `package.nls.json` and `package.nls.zh-cn.json`.
3. There's no automated symmetry test for nls files (they're JSON, not TS modules). Manual review in code review.

## What NOT to localize

- Internal comments — the codebase comments in Chinese (matching the primary user), English technical terms inline.
- Console.warn/error strings — diagnostic, never user-facing.
- File paths, env var names, command IDs — these are identifiers, not text.
- Build artifacts in `dist/` — generated, never read by humans.
